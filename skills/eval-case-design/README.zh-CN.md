# Eval Case Design

`eval-case-design` 是一个可移植的 Skill：把 Agent 或工具的行为做成固定评测集，用结构化的通过/失败判定和一条确定性基线来衡量，让报出的通过率可以被复现。

English: [README.md](README.md)

## 它能做什么

- 列出要测的行为：正常路径、需要追问澄清、业务规则拒绝、非法输入、系统故障。
- 每种行为先固定一条用例再开始跑，其中至少有一条输入含糊或故意刁难的用例。
- 按工具名、参数、返回码和最终状态打分。自由文本像不像，不作为主要依据。
- 每条用例单独准备状态，原始结果和失败都留着。
- 重复跑 N 次，报告每条用例的通过次数、汇总，以及样本量、模型、版本和日期。
- 用规则或正则做成的确定性基线做对照。

## 为什么需要它

用例没固定、判定不结构化、旁边没有基线时，通过率说明不了什么。先把用例写死，也避免为了让某次实现“过关”而事后改预期。

## 何时使用

- Agent 或工具有一项行为需要衡量。
- 准备说“能用了”，但需要审查者可以自己复现的依据。
- 要和一条不用 Agent 的基线对照。

## 在编程 Agent 中使用

1. 将当前 Skill 文件夹复制到目标编程 Agent 支持的 Skills 目录。
2. 说明要衡量的行为，要求 Agent 使用 `eval-case-design`，先写用例、先不跑。
3. 审用例集。此后预期不再改。
4. 再要求做检查器、跑 N 次、对照基线，并在报告里保留失败。

可直接使用的指令：

> 请使用 `eval-case-design` Skill。列出行为，每种写一条固定用例，其中包含一条输入含糊或故意刁难的用例。先停下，不要运行。我接受用例之后，再按结构化信号做检查器，每条用例用干净状态跑 N 次，补上确定性基线，并报告样本量、模型、版本、日期、失败项和局限。

## 规则

- 先固定用例再运行。不要为了让实现通过而去改预期。
- 依据结构化信号判断：工具名与参数、返回码、最终状态。
- 不要把自由文本的相似度当作主要依据。
- 一种行为一条用例，并至少包含一条输入含糊或故意刁难的用例。
- 每条用例使用全新状态（临时数据库，或先重置再使用的测试数据）。
- 保留原始结果，失败也留着。
- 必须有基线，否则通过率说明不了多少。
- 报告样本量、模型、版本和日期。
